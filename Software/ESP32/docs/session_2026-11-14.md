## 1. Symptom

TEST on `http://<target-ip>:8080/remote` always gave:

```
Last server status: Connection failed - Test shot sent
```

"Connection failed" means `http_post_last_status = -1`, i.e. `esp_http_client_perform()` failed
(`main/TCPIP/http_client.c`, `http_post_task()`). "Test shot sent" only reports that the button was pressed.

With `{"TRACE":16}` (`DLT_COMMUNICATION`) on the USB console:

```
C (43.216) POST https://markering.ou-taa.dk/api/skydninger {"shot":0, "test":1}
E (50987) esp-tls: [sock=62] select() timeout
E (50997) esp-tls: Failed to open new connection
E (50997) transport_base: Failed to open a new connection
E (50997) HTTP_CLIENT: Connection failed, sock < 0
```

DNS worked (otherwise `couldn't get hostname`), but the TCP connection was never established.

| Client isolation | Not relevant: it only blocks WiFi client-to-client traffic, not traffic to the gateway |

## 4. Cause: a private copy of the lwIP socket layer

`main/drivers/sockets.c` is an old copy of lwIP's `sockets.c` (`lwip_socket()`, `lwip_connect()`,
`lwip_select()` …). `main/CMakeLists.txt` builds every file under `main/` with `GLOB_RECURSE`, so the copy was
linked in and replaced the ESP-IDF version. Confirmed in `build_local/freeETarget.map`:

```
.text.lwip_connect  0x42016abc  0x10a  esp-idf/main/libmain.a(sockets.c.obj)
```

The copy does not match the lwIP headers of ESP-IDF v5.3.5, and outgoing connections went to the wrong port.
The exact mechanism was not found (the port conversion macros are identical to ESP-IDF's), but the
fault disappeared as soon as the file was taken out of the build.

## 5. Knock-on fault: the port 8080 server did not start

Without the old `sockets.c` the second web server failed at start-up:

```
I (10.905) start_webserver(port: 8080)
E (13615) httpd: httpd_server_init: error in creating ctrl socket (112)
E (10.916) Error starting server!
```

112 = `EADDRINUSE`. Both servers (port 80 and 8080) used the default control port
`ESP_HTTPD_DEF_CTRL_PORT` (32768). The old socket copy never noticed the clash.

## 7. Realistic test shot

The old test shot `{"shot":0, "test":1}` was rejected by the server with **HTTP 400**.
TEST now builds a `shot_record_t` and sends it through `build_json_score(&shot, SCORE_TCPIP)` – the same fields
as a real shot. The server answers **HTTP 201** and stores the test shot like any other shot.

The position was refined in a few steps at the user's request:
1. random within ±5 mm of the centre,
2. random angle at exactly 20 mm,
3. random angle and a uniform radius of 0–20 mm (crowds the shots near the centre),
4. **evenly spread over the circle**: `r = R · √u`, where `u` is uniform in [0, 1]. A ring of width dr at
   radius r has an area proportional to r; the square root compensates for this,
5. in 6.5.2: `R` = **25 mm**, shared with the switch test shot (section 8).

Example (the key is sent as an `X-API-KEY` header and is therefore not in the body):

```json
{"shot":2, "session_type":1, "time":19700, "time_to_go":110, "x":19.44, "y":4.80, "athelete":"Ole", "event":"Pistol Practice", "target_name":"freETarget.targets.AirPistol"}
```

## 8. PC TEST switch shot is POSTed too (6.5.2, commit `9d64caa`)

The two multifunction switches can be set to send a fake shot to the PC, e.g. `{"MFS_TAP_2":4}`
(`PC_TEST`, `main/mfs.h:55`, action table in `main/mfs.c`). This runs `mfs_test_build_json_score()`
(`main/diag_tools.c`), which sent the shot to USB, TCP/IP and AUX, but not to the REST server.

Changes:

| File | Change |
|---|---|
| `main/diag_tools.c`, `diag_tools.h` | New `build_test_shot(shot_record_t *shot)`: fills in shot, `session_type`, `shot_time`, radius, angle, `x_mm`/`y_mm` (even spread, `TEST_SHOT_RADIUS` = 25 mm). Used by every source of test shots |
| `main/diag_tools.c` | One shot counter (`test_shot_count`) shared by all sources – the web TEST now counts up as well (1, 2, 3 … until restart) |
| `main/diag_tools.c` | `mfs_test_build_json_score()` calls `http_post_shot()` with the TCP/IP score (does nothing unless `REMOTE_ACTIVE` and `REMOTE_URL` are set) |
| `main/diag_tools.c` | The fake shot uses a local record instead of `record[0]`, which used to overwrite the first real shot of the session |
| `main/diag_tools.c` | Score copy buffer 1024 bytes (was `LARGE_STRING`, 128) and always terminated – see below |
| `main/TCPIP/http_services.c` | The `/remote` TEST button calls `build_test_shot()` instead of its own generator |
| `main/freETarget.h`, `sdkconfig` | Version `6.5.2 November 14, 2026`, `CONFIG_APP_PROJECT_VER="60502"` |

**Bug found while testing:** the first PC TEST was rejected with **HTTP 400**. The score was copied into
`char str[LARGE_STRING]` (128 bytes). With the athlete, event and target names set the score is longer, and
`strncpy()` left it truncated and unterminated (the console showed the body ending in `"event":"Pistol Practice",^B`).
The same truncation also affected the line sent to the PC.

The diagnostic menu entry "build_json_score" calls the same function, so it POSTs too. It can be run with
`{"TEST":150}` (`{"TEST":999}` lists the numbers) – that is how the switch action was tested without pressing the button.

Verified on target 421:

| Source | Shot | Distance from centre | Reply |
|---|---|---|---|
| Web TEST | 1 | 22.7 mm | HTTP 201 |
| Web TEST | 2 | 20.0 mm | HTTP 201 |
| PC TEST (diagnostic menu) | 3 | 9.4 mm | HTTP 201 |

The physical button itself was not pressed during the session.

## 9. Build and flash without an ESP-IDF terminal

`export.ps1` did not put `idf.py` on the PATH in a plain PowerShell. Setting up the environment by hand works:

```powershell
$env:IDF_PATH='C:\Espressif\frameworks\esp-idf-v5.3.5'; $env:IDF_TOOLS_PATH='C:\Espressif'
$py='C:\Espressif\python_env\idf5.3_py3.11_env\Scripts\python.exe'
foreach ($l in (& $py "$env:IDF_PATH\tools\idf_tools.py" export --format key-value)) {
  $k,$v = $l -split '=',2
  if ($k -eq 'PATH') { $v = $v -replace '%PATH%',$env:PATH -replace '\$PATH',$env:PATH }
  Set-Item "env:$k" $v
}
& $py "$env:IDF_PATH\tools\idf.py" -B build_local -p COM4 flash
```

The warning about a missing `idf_version.txt` can be ignored. Flashing fails with "Access denied" if a serial monitor
has COM4 open.

The target (serial no. 421, `FET-TARGET`) now runs **6.5.2** (`/who`: `6.5.2 November 14, 2026` / OTA `60502`).
