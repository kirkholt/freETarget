## 3. Build a bin file for a firmware upgrade

```
idf.py -B build_local build
```

Run in an ESP-IDF terminal (ESP-IDF v5.3.5, `C:\Espressif\frameworks\esp-idf-v5.3.5`).
In a plain PowerShell Python is not on the PATH, so ESP-IDF's own Python environment
(`C:\Espressif\python_env\idf5.3_py3.11_env`) must be used.

Result: `build_local\freeETarget.bin` (1,376,352 bytes, < 2 MB OTA partition).

**Upgrading:**
- **Network OTA:** put the file as `freeETarget.bin` (exactly that name) in the folder `OTA_URL` points to
  (default `http://targetbin.app/OTA/freeETarget.bin`), and send `{"OTA":0}`.
  `OTA_load()` in `main/TCPIP/OTA.c:86` fetches `<OTA_URL>/freeETarget.bin`.
- **Serial:** the PC tool using the `{"DOWNLOAD": <size>}` protocol (`OTA_serial()`, `OTA.c:314`).

`OTA_check_header()` (`OTA.c:476`) compares the OTA version character by character and rejects the same or an older version.
→ `CONFIG_APP_PROJECT_VER` must be raised for every release.

## 4. Can the new file replace `freeETarget_6_4_2.bin`?

Yes. Comparison of the image headers and `esptool image_info`:

| | `freeETarget_6_4_2.bin` | new `freeETarget.bin` |
|---|---|---|
| Chip | ESP32-S3 (id 9) | ESP32-S3 (id 9) |
| Flash mode/size/frequency | DIO, 8 MB, 80 MHz | same |
| Project name | `freeETarget` | `freeETarget` |
| Segments | 6 | 6 |
| Checksum + SHA-256 | valid | valid |
| OTA version | `60301` | `60500` |
| Firmware text | 6.4.2 July 19, 2026 | 6.5.0 October 26, 2026 |
| ESP-IDF | v5.3.1-dirty | v5.3.5 |
| Size | 1,299,520 bytes | 1,376,352 bytes |

- `60500` > `60301` → OTA accepts the update.
- IDF v5.3.1 → v5.3.5 is a patch level; the bootloader is not replaced by OTA.
- Not tried on a physical target.

## 5. Downgrading to 6.4.2 over USB

Flashing over USB with `esptool` bypasses `OTA_check_header()`, so a downgrade is possible.
After an OTA the target boots from `ota_0`/`ota_1` (controlled by `ota_data` at 0xd000), so `ota_data` must be reset:

```
python -m esptool --chip esp32s3 -p COMx -b 460800 write_flash 0xd000 build_local\ota_data_initial.bin 0x10000 freeETarget_6_4_2.bin
```

- NVS (settings at 0x9000) is kept.
- 6.4.2 has `PS_VERSION` 17; NVS has 18. `update_nonvol()` runs 0 times and stores 17 – harmless.
  The REMOTE keys stay in NVS without being used.
- On a later upgrade to 6.5.0 the 17→18 update runs again; the REMOTE setup will probably have to be entered again.
- Do not use `idf.py flash` to downgrade – it flashes the built project (6.5.0).

## 6. Must the target be initialised before shots are recorded?

No. `freETarget_target_loop()` (`main/freETarget.c:228`) calls `start_new_session(0)` at start-up,
sets `shot_number = 1` and `run_state |= IN_SHOT`. The state machine `START → arm() → WAIT → REDUCE → START`
re-arms automatically after every shot.

Things that can stop shots being recorded:
- A sensor that is already triggered when arming (`arm()` shows an error and tries again).
- Power save (`POWER_SAVE` ≠ 0 → `IN_SLEEP` after N minutes without shots; default 0 = off).
- `IN_TEST` / `IN_FATAL_ERR`.
- Shots with < 4 valid sensors (sensor error, no result).

HTTP POST (`http_post_shot()`, `main/TCPIP/http_client.c:632`) needs `REMOTE_ACTIVE`=1, `REMOTE_URL` set and WiFi.
Stored in NVS – no command per session. Misses are not POSTed.

## 7. Where/how is `start_new_session()` called?

Defined in `main/freETarget.c:563`. Called from:
1. Start-up – `freETarget.c:241`, always `0`.
2. JSON `{"SESSION": <type>}` – `json.c:106` (USB, AUX, TCP/IP).
3. New connection – `serial_io.c:1042`, `check_new_connection()`, with `json_session_type` (only ≤ 1 connection).
4. Web menu – `http_services.c:381`.

| Value | Effect |
|---|---|
| `0` (and unknown) | Clear all shots, reset `shot_in`/`shot_out` and run time |
| `2` | Sighters, 15 min timer, shots kept |
| `4` | Match, 75 min timer, shots kept |
| `10` / `12` / `14` | Resend all / sighter / match shots (also via `http_post_shot()`) |

Bit 0 (`SESSION_VALID`) is masked off. `event_override()` is always called.

**Observation (not fixed):** the web menu calls `start_new_session(check_mask & SIGHT)`, where `SIGHT` = 1 in
`http_services.c`. The result is always 0/1 → every START button just clears the session and starts no timer.

Observations (from the code, not tried):

- STOP is recognised but does nothing.

## 9. URL for START

```
http://<target-ip>:8080/menu?START
```

`contains()` (`main/helpers.c:189`) is case-insensitive. Effect: clears the shots, new empty session.

## 10. Send `{"SESSION":4}` via `/json`

```
http://<target-ip>/json?{"SESSION":4}
```

curl:
```
curl "http://192.168.1.50/json?%7B%22SESSION%22:4%7D"
curl -g "http://192.168.1.50/json?{\"SESSION\":4}"
```

`squish()` (`main/helpers.c:653`) takes everything after the first `?` and decodes `%xx`.
The command is put on the TCP/IP queue (`service_get_json()`, `http_services.c:656`); the reply comes after ≥ 1 second.

## 11. Set `REMOTE_URL` via `/json`

```
http://<target-ip>/json?{"REMOTE_URL":"https://my.server.com/api/shots"}
http://<target-ip>/json?{"REMOTE_URL":"https://my.server.com/api/shots","REMOTE_KEY":"<guid>","REMOTE_ACTIVE":1}
```

curl:
```
curl "http://192.168.1.50/json?%7B%22REMOTE_URL%22:%22https://my.server.com/api/shots%22%7D"
```

- Stored in NVS immediately (`json.c:378`).
- Max. 128 characters (`URL_SIZE`, `json.h:75`); the length is not checked.
- Include `http://` / `https://`.
- Avoid `%` and `#` in the URL; `?` and `&` are OK.
- The REMOTE fields are marked `LOCK` (`json.c:98-101`) – unlock the target first if it is locked.
- Alternative: the form at `http://<target-ip>:8080/remote`.
- Check: `/json?{"REMOTE_URL"}` or `/json?{"ECHO":1}`.

## 12. Data structure POSTed to `REMOTE_URL`

Each shot is sent as one JSON object in an HTTP POST with `Content-Type: application/json`.
The object is built by `build_json_score(&record, SCORE_TCPIP)` (`main/helpers.c:474`) with the format `"{S?TXE}"`
(`main/freETarget.h:125`) and sent by `http_post_task()` (`main/TCPIP/http_client.c:710`).

Example:

```json
{"shot":3, "session_type":5, "time":84213, "time_to_go":4500, "x":-4.12, "y":7.80, "athelete":"Ole", "event":"Match", "target_name":"TARGET1", "apikey":"<REMOTE_KEY>"}
```

| Field | Source | Meaning |
|---|---|---|
| `shot` | `shot->shot + 1` | Shot number, starts at 1 |
| `session_type` | `SESSION_VALID \| json_session_type` | `1` = no session, `3` = sighters, `5` = match |
| `time` | `run_time_ms()` at the shot | Milliseconds since the session started |
| `time_to_go` | global `time_to_go` | The value set by `start_new_session()`: 900 (sighters), 4500 (match), 1000 (empty). Not checked whether it counts down |
| `x`, `y` | `x_mm`, `y_mm` | Position in mm, 2 decimals |
| `athelete` | `json_athlete` | Shooter's name – misspelt in the code; the server must use exactly `athelete` |
| `event` | `json_event` | Event name |
| `target_name` | `json_target_name` | The target's name |
| `apikey` | `REMOTE_KEY` | Only when `REMOTE_KEY_MODE` = 0 and the key is not empty |

Variations:
- `REMOTE_KEY_MODE` = 1: the key is sent as the header `X-API-KEY: <key>`, and `apikey` is left out of the body.
- Trace `DLT_SCORE` on: the raw counter values `"n"`, `"e"`, `"s"`, `"w"` are added at the end.
- `build_json_score()` starts with `{{{{{` to wake up the PC client; `http_post_shot()` removes the extra braces so the server gets valid JSON.
- Max. body 640 bytes (`HTTP_POST_PAYLOAD_SIZE`), max. 8 shots in the queue (`HTTP_POST_QUEUE_SIZE`; full queue → the newest shot is dropped),
  timeout 5 seconds (`HTTP_POST_TIMEOUT_MS`).

Not sent: score/ring (the server must compute it from `x`/`y`), polar coordinates (`r`, `a`), target type (`target`).
Misses are not POSTed at all.

The structure was read from the code; a real POST from a target has not been observed.

**Observation (not fixed):** the comment in `http_client.c:547` says `/remote` is on port 81, but it is registered on 8080.
