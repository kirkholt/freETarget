## 1. Hvilken version har firmwaren?

Firmwaren var **6.4.2** (19. juli 2026), defineret i `main/freETarget.h:22`:

```c
#define SOFTWARE_VERSION "\"6.4.2 July 19, 2026\""
```

Persistent storage-version: `PS_VERSION` = **18** (`main/nonvol.h:11`).

## 2. Opdater versionen til 6.5.0

- `main/freETarget.h:22` → `#define SOFTWARE_VERSION "\"6.5.0 October 26, 2026\""`
- `sdkconfig:455` → `CONFIG_APP_PROJECT_VER="60500"` (var forældet `60301`)

`CONFIG_APP_PROJECT_VER` er værdien i `running_app_info.version`, som OTA bruger til versionstjek og som vises på status-/web-siderne.
`sdkconfig.old` og `CONFIG_BOOTLOADER_PROJECT_VER` blev ikke ændret.

Committet som `900e6ea` "Bump firmware version to 6.5.0" og pushet til `origin/feature/http-post-shots`.
`dependencies.lock` (ændret før sessionen) og `freeETarget_6_4_2.bin` (untracked) er ikke committet.

## 3. Byg en bin-fil til firmware-opgradering

```
idf.py -B build_local build
```

Køres i en ESP-IDF-terminal (ESP-IDF v5.3.5, `C:\Espressif\frameworks\esp-idf-v5.3.5`).
I en almindelig PowerShell findes Python ikke på PATH, så ESP-IDF's eget Python-miljø
(`C:\Espressif\python_env\idf5.3_py3.11_env`) skal bruges.

Resultat: `build_local\freeETarget.bin` (1.376.352 bytes, < 2 MB OTA-partition).

**Opgradering:**
- **Netværks-OTA:** læg filen som `freeETarget.bin` (præcis det navn) i mappen `OTA_URL` peger på
  (standard `http://targetbin.app/OTA/freeETarget.bin`), og send `{"OTA":0}`.
  `OTA_load()` i `main/TCPIP/OTA.c:86` henter `<OTA_URL>/freeETarget.bin`.
- **Serielt:** PC-værktøjet med `{"DOWNLOAD": <størrelse>}`-protokollen (`OTA_serial()`, `OTA.c:314`).

`OTA_check_header()` (`OTA.c:476`) sammenligner OTA-versionen tegn for tegn og afviser samme eller ældre version.
→ `CONFIG_APP_PROJECT_VER` skal hæves ved hver release.

## 4. Kan den nye fil erstatte `freeETarget_6_4_2.bin`?

Ja. Sammenligning af image-headere og `esptool image_info`:

| | `freeETarget_6_4_2.bin` | ny `freeETarget.bin` |
|---|---|---|
| Chip | ESP32-S3 (id 9) | ESP32-S3 (id 9) |
| Flash mode/størrelse/frekvens | DIO, 8 MB, 80 MHz | samme |
| Projektnavn | `freeETarget` | `freeETarget` |
| Segmenter | 6 | 6 |
| Checksum + SHA-256 | gyldige | gyldige |
| OTA-version | `60301` | `60500` |
| Firmwaretekst | 6.4.2 July 19, 2026 | 6.5.0 October 26, 2026 |
| ESP-IDF | v5.3.1-dirty | v5.3.5 |
| Størrelse | 1.299.520 bytes | 1.376.352 bytes |

- `60500` > `60301` → OTA accepterer opdateringen.
- IDF v5.3.1 → v5.3.5 er patch-niveau; bootloaderen skiftes ikke ved OTA.
- Ikke afprøvet på en fysisk target.

## 5. Nedgradering til 6.4.2 via USB

USB-flash med `esptool` går uden om `OTA_check_header()`, så nedgradering er mulig.
Efter en OTA booter target'en fra `ota_0`/`ota_1` (styret af `ota_data` på 0xd000), så `ota_data` skal nulstilles:

```
python -m esptool --chip esp32s3 -p COMx -b 460800 write_flash 0xd000 build_local\ota_data_initial.bin 0x10000 freeETarget_6_4_2.bin
```

- NVS (indstillinger på 0x9000) bevares.
- 6.4.2 har `PS_VERSION` 17; NVS har 18. `update_nonvol()` kører 0 gange og gemmer 17 – harmløst.
  REMOTE-nøglerne bliver liggende uden at blive brugt.
- Ved senere opgradering til 6.5.0 køres 17→18-opdateringen igen; REMOTE-opsætningen skal sandsynligvis indtastes igen.
- Brug ikke `idf.py flash` til nedgradering – den flasher det byggede projekt (6.5.0).

## 6. Skal target initialiseres før skud registreres?

Nej. `freETarget_target_loop()` (`main/freETarget.c:228`) kalder ved opstart `start_new_session(0)`,
sætter `shot_number = 1` og `run_state |= IN_SHOT`. Tilstandsmaskinen `START → arm() → WAIT → REDUCE → START`
genarmerer automatisk efter hvert skud.

Kan forhindre registrering:
- Sensor der allerede trigger ved armering (`arm()` viser fejl og prøver igen).
- Strømspare (`POWER_SAVE` ≠ 0 → `IN_SLEEP` efter N minutter uden skud; standard 0 = fra).
- `IN_TEST` / `IN_FATAL_ERR`.
- Skud med < 4 gyldige sensorer (sensorfejl, intet resultat).

HTTP POST (`http_post_shot()`, `main/TCPIP/http_client.c:632`) kræver `REMOTE_ACTIVE`=1, `REMOTE_URL` sat og WiFi.
Gemmes i NVS – ingen kommando pr. session. Misses POSTes ikke.

## 7. Hvor/hvordan kaldes `start_new_session()`?

Defineret i `main/freETarget.c:563`. Kaldes fra:
1. Opstart – `freETarget.c:241`, altid `0`.
2. JSON `{"SESSION": <type>}` – `json.c:106` (USB, AUX, TCP/IP).
3. Ny forbindelse – `serial_io.c:1042`, `check_new_connection()`, med `json_session_type` (kun ≤ 1 forbindelse).
4. Webmenu – `http_services.c:381`.

| Værdi | Effekt |
|---|---|
| `0` (og ukendte) | Ryd alle skud, nulstil `shot_in`/`shot_out` og køretid |
| `2` | Prøveskud, 15 min timer, skud bevares |
| `4` | Match, 75 min timer, skud bevares |
| `10` / `12` / `14` | Send alle / prøve- / match-skud igen (også via `http_post_shot()`) |

Bit 0 (`SESSION_VALID`) maskeres væk. `event_override()` kaldes altid.

**Observation (ikke rettet):** webmenuen kalder `start_new_session(check_mask & SIGHT)`, hvor `SIGHT` = 1 i
`http_services.c`. Resultatet er altid 0/1 → alle START-knapper rydder blot sessionen og starter ingen timer.

| `/help` | Hjælp |

**Port 8080:**

| URL | Indhold |
|---|---|
| `/` eller `/menu` | Kontrolmenu (`main/HTML/menu.html`) |
| `/remote` | REST-server-opsætning (REMOTE_ACTIVE, URL, nøgle, nøgletilstand) |
| `/help` | Hjælp |

Menuen: valg af skive (10m Air Pistol/Rifle, 50m Pistol/Rifle), event (SIGHT/MATCH), START, STOP og link til `/remote`.

Observationer (fra koden, ikke afprøvet):
- START rydder skud (typisk to kald til `start_new_session()`); skive/event-valg gemmes ikke (`session_type` beregnes men bruges ikke).
- STOP genkendes men gør intet.
- `menu.html:115` mangler `=` efter `onclick` (kosmetisk).

## 9. URL til START

```
http://<target-ip>:8080/menu?START
```

`contains()` (`main/helpers.c:189`) er case-insensitiv. Effekt: rydder skud, ny tom session.

## 10. Send `{"SESSION":4}` via `/json`

```
http://<target-ip>/json?{"SESSION":4}
```

curl:
```
curl "http://192.168.1.50/json?%7B%22SESSION%22:4%7D"
curl -g "http://192.168.1.50/json?{\"SESSION\":4}"
```

`squish()` (`main/helpers.c:653`) tager alt efter første `?` og afkoder `%xx`.
Kommandoen lægges i TCP/IP-køen (`service_get_json()`, `http_services.c:656`); svaret kommer efter ≥ 1 sekund.

## 11. Sæt `REMOTE_URL` via `/json`

```
http://<target-ip>/json?{"REMOTE_URL":"https://min.server.dk/api/shots"}
http://<target-ip>/json?{"REMOTE_URL":"https://min.server.dk/api/shots","REMOTE_KEY":"<guid>","REMOTE_ACTIVE":1}
```

curl:
```
curl "http://192.168.1.50/json?%7B%22REMOTE_URL%22:%22https://min.server.dk/api/shots%22%7D"
```

- Gemmes straks i NVS (`json.c:378`).
- Maks. 128 tegn (`URL_SIZE`, `json.h:75`); længden tjekkes ikke.
- Medtag `http://` / `https://`.
- Undgå `%` og `#` i URL'en; `?` og `&` er OK.
- REMOTE-felterne er `LOCK`-markeret (`json.c:98-101`) – lås target op først, hvis den er låst.
- Alternativ: formularen på `http://<target-ip>:8080/remote`.
- Tjek: `/json?{"REMOTE_URL"}` eller `/json?{"ECHO":1}`.

## 12. Datastruktur der POSTes til `REMOTE_URL`

Hvert skud sendes som ét JSON-objekt i en HTTP POST med `Content-Type: application/json`.
Objektet bygges af `build_json_score(&record, SCORE_TCPIP)` (`main/helpers.c:474`) med formatet `"{S?TXE}"`
(`main/freETarget.h:125`) og sendes af `http_post_task()` (`main/TCPIP/http_client.c:710`).

Eksempel:

```json
{"shot":3, "session_type":5, "time":84213, "time_to_go":4500, "x":-4.12, "y":7.80, "athelete":"Ole", "event":"Match", "target_name":"TARGET1", "apikey":"<REMOTE_KEY>"}
```

| Felt | Kilde | Betydning |
|---|---|---|
| `shot` | `shot->shot + 1` | Skudnummer, starter ved 1 |
| `session_type` | `SESSION_VALID \| json_session_type` | `1` = ingen session, `3` = prøveskud, `5` = match |
| `time` | `run_time_ms()` ved skuddet | Millisekunder siden sessionen startede |
| `time_to_go` | global `time_to_go` | Værdien sat af `start_new_session()`: 900 (prøve), 4500 (match), 1000 (tom). Ikke tjekket om den tæller ned |
| `x`, `y` | `x_mm`, `y_mm` | Position i mm, 2 decimaler |
| `athelete` | `json_athlete` | Skyttens navn – stavet forkert i koden; serveren skal bruge præcis `athelete` |
| `event` | `json_event` | Eventnavn |
| `target_name` | `json_target_name` | Target'ens navn |
| `apikey` | `REMOTE_KEY` | Kun når `REMOTE_KEY_MODE` = 0 og nøglen ikke er tom |

Variationer:
- `REMOTE_KEY_MODE` = 1: nøglen sendes som header `X-API-KEY: <key>`, og `apikey` udelades fra body.
- Trace `DLT_SCORE` slået til: de rå tællerværdier `"n"`, `"e"`, `"s"`, `"w"` tilføjes sidst.
- `build_json_score()` starter med `{{{{{` for at vække PC-klienten; `http_post_shot()` fjerner de ekstra klammer, så serveren får gyldig JSON.
- Maks. body 640 bytes (`HTTP_POST_PAYLOAD_SIZE`), maks. 8 skud i kø (`HTTP_POST_QUEUE_SIZE`; fuld kø → nyeste skud droppes),
  timeout 5 sekunder (`HTTP_POST_TIMEOUT_MS`).

Sendes ikke: score/ring (serveren må beregne fra `x`/`y`), polære koordinater (`r`, `a`), skivetype (`target`).
Misses POSTes slet ikke.

Strukturen er læst ud af koden; en rigtig POST fra en target er ikke observeret.

**Observation (ikke rettet):** kommentaren i `http_client.c:547` siger, at `/remote` ligger på port 81, men den er registreret på 8080.
